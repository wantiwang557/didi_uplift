# v6_dfcl_touch 样本 SQL

> 已被 `../v6_dfcl_episode/` 的最新业务口径替代，请勿用于最终取数。旧目录仅保留用于对照固定7天分块方案。

本目录是在原 `v6` 特征 SQL 上新增的“触达锚点 + 7 天候选周期”取样版本。原 `v6` 文件保持不变。

## 输出文件

- `feature_v6_dfcl_touch_train.sql`：2026-07-16 ～ 2026-08-21
- `feature_v6_dfcl_touch_valid.sql`：2026-08-22 ～ 2026-08-27
- `feature_v6_dfcl_touch_test.sql`：2026-08-28 ～ 2026-09-10

三个 SQL 保留原 v6 的特征列、`label`、`exp_label`、`cost_7d`、`fake_treatment_id`、`flag` 和 `label_dt`。变化仅发生在样本选择逻辑。

## 已确认业务口径

1. `send_success_cnt > 0` 或 `outcall_success_cnt > 0` 表示当天触达/发券成功，这两个字段不是历史累计值。
2. 发券成功后，以成功日为锚点，券有效期为自然日 7 天（锚点日到锚点日 + 6 天）。
3. 发券失败会继续触达。成功前 6 天内且未被前一成功窗口覆盖的失败记录，并入下一次成功候选周期。
4. 一个候选周期内：
   - 只要存在 `finish_cnt_7d > 0` 的归因记录，就保留正记录；若罕见地有多条正记录，先取 `finish_cnt_7d` 最大的，再取日期较晚的。
   - 全部为 0 时，成功候选保留触达成功日；没有成功锚点的候选保留最后一条。
5. control 没有发券成功日；连续失败也可能没有成功日。按已经确认的临时约定，从完整历史内该用户首次可观测入组日开始，每 7 个自然日切一个固定窗口。这是建模去重口径，不代表真实发券批次。
6. 完单的“外呼成功 > 短信成功 > 末次入组”归因已经体现在源表 `finish_cnt_7d` 中，本 SQL 不重新归因订单。

## 安全筛选

基础筛选与原 v6 一致：

- `new_exp = '迭代流量'`
- 只保留 control + 4 个 treatment
- `pid is not null`
- 排除原 v6 的异常日期

另外，下面这些不能唯一确定样本含义的数据不会进入最终结果：

- 同一用户在历史中出现多个 treatment；
- 同一用户同一天出现多个实验组键；
- 同一天同一实验组键的标签/触达/成本字段互相冲突；
- `finish_cnt_7d` 为 null 或小于 0。

完全相同的标签源记录会先折叠，不会重复进入候选周期。

不再使用原 SQL 中依赖结果变量的 `finish_all_cnt` 筛选。control 的最终 `cost_7d` 强制为 0。

## EUEN 与 DFCL 的使用

- 两者都从这套未采样的统一基础样本出发。
- DFCL 使用完整基础样本，并按 treatment 查固定 propensity：`0.4916 / 0.1778 / 0.1185 / 0.0935 / 0.1186`。
- EUEN 如需正负采样，只能在这套基础样本生成之后、模型训练阶段执行；valid/test 不采样。
- 由于样本分布已经变化，需新建一个特征配置 profile：只在新 train 上拟合离散边界，valid/test 复用该 train 配置。不要直接把旧 v6 已拟合的分桶边界当作新 profile 的最终配置。

## 当前限制

- 没有业务侧真实 `incentive_id`/发券批次号时，无成功锚点的 7 天轮次只能采用上述固定窗口近似。
- SQL 选择的是源表已经归因到某条入组记录的 `finish_cnt_7d` 和 `cost_7d`，不重新聚合一个候选周期内所有失败重试的执行成本。
- 三份 SQL 尚需在 Spark/Hive 集群上进行小窗口验收，再全量产出。

建议先运行相邻目录 `v6_dfcl_touch_audit/sample_cases_query.py` 查看真实 case，再核对最终样本量、组别分布、正样本率、异常剔除量和 treatment propensity。
