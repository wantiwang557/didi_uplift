# EUEN 用户级在线运筹流程与 DFCL 接入方案

> 适用范围：WWT 多 treatment 补贴场景。本文记录当前在线运筹代码的运行逻辑、预测数据与后验数据的分工、候选参数选择规则，以及 DFCL 接入现有 EUEN 的推荐方式。

## 1. 核心结论

当前系统应拆成三个层次：

1. **DFCL 用于离线训练**：在 EUEN 原有 outcome/cost 预测损失上增加决策损失，让模型输出更适合最终资源分配。
2. **拉格朗日规则用于在线决策**：线上读取 EUEN 对每个用户、每个动作的 uplift/cost 预测及已发布的 `C、lambda`，逐用户计算分数并选择动作。
3. **成熟 RCT 后验用于异步反馈**：7 日标签成熟后，用于离线训练、策略回放、`C、lambda` 校准和上线门禁，不直接参与当天新用户的动作计算。

因此，DFCL 不是在“离线”和“在线”中二选一。准确说法是：

```text
离线：EUEN + DFCL decision loss 训练
在线：EUEN 推理 + 拉格朗日逐用户选动作
异步：成熟 RCT 后验回放并更新模型或 C、lambda
```

## 2. 原分桶运筹中的后验位置

原流程为：

```text
EUEN 预测
  -> 按预测 uplift/cost 和业务特征分桶
  -> 在历史成熟 RCT 中按“桶 × 实际实验组”聚合
  -> 计算每桶每动作相对 control 的后验订单和成本
  -> OR-Tools 为每个桶选择一个动作
  -> 将新用户映射到桶并执行桶动作
```

后验数据位于“分桶之后、OR 求解之前”，是 OR 收益矩阵和成本矩阵的直接输入。使用的数据主要包括：

- 实际 RCT 组 `group_name_eve`；
- 7 日订单标签 `pv_label_7d` / `uv_label_7d`；
- 7 日成本 `cost_7d`。

这套方法的优点是桶内聚合稳定，缺点是同一桶只能采用相同动作，而且模型只负责分桶，预测误差是否影响最终决策没有直接反传到训练目标。

## 3. 用户级在线运筹的完整流程

### 3.1 慢循环：历史参数更新

假设标签需要 7 天成熟，每次定时任务使用两个不重叠的历史窗口：

- 求解窗口：根据模型预测为每个候选 `C` 求 `lambda`；
- 验证窗口：冻结候选参数，用成熟 RCT 后验评价策略；
- 只有候选策略通过后验门禁时，才更新线上参数表。

对于用户 `i` 和动作 `a`，在线运筹代码使用：

```text
score(i,a) = delta_y_hat(i,a)
             + lambda * (C * delta_y_hat(i,a) - cost_hat(i,a))
```

control 的分数为 0。给定 `C、lambda` 后，逐用户选择：

```text
action(i) = argmax_a score(i,a)
```

对每个候选 `C`，`lambda` 通过最小化预测对偶目标得到。这一步只使用模型预测，不使用真实 7 日标签。

### 3.2 后验回放

得到候选 `C、lambda` 后，将其应用到验证窗口：

1. 只根据历史用户当时的模型预测，重新生成每个人的推荐动作；
2. 按“推荐动作”形成推荐层；
3. 在每个推荐层内部，用实际 treatment 与 control 的成熟结果计算订单和成本差；
4. 汇总所有推荐层，得到策略的后验增量订单、增量成本和增量 CAC。

这里模型预测负责决定“当前策略会推荐什么”，成熟 RCT 后验负责回答“这个推荐策略实际上有没有价值”。两者不能混用，验证时也不能根据真实标签反过来修改单个用户的推荐动作。

### 3.3 快循环：当天新用户决策

参数发布后，当天新用户只使用：

- 当前用户特征；
- EUEN 输出的各动作 uplift/cost 预测；
- 参数表中的 `C、lambda`。

当天新用户尚未产生 7 日结果，因此不会使用 `pv_label_7d` 或 `cost_7d`。四动作场景的计算复杂度约为 `O(N * 4)`，不需要对用户执行大规模整数规划。

### 3.4 反馈闭环

当天策略执行后，需要保留随机实验或 control holdout。7 日后标签成熟，形成下一轮可用的后验数据：

```text
用户进入 RCT / 探索流量
  -> 当时生成并冻结模型预测
  -> 7 日结果成熟
  -> 后验回放与参数选择
  -> 发布 C、lambda
  -> 新用户逐人决策
  -> 新一批 RCT 后验成熟
```

如果所有用户都确定性执行推荐动作且没有随机 control，就只能观察策略结果，无法可靠估计未选动作的反事实效果，也无法继续进行无偏后验回放或 DFCL 的因果决策训练。

## 4. 在线代码的候选参数规则

### 4.1 候选生成

当前默认候选 `C` 为：

```text
4.0, 4.1, ..., 5.9
```

候选范围来自人工配置，不是自动学习结果。每个 `C` 在求解窗口上根据预测 uplift/cost 单独求一个 `lambda`，形成候选参数对 `(C, lambda)`。

### 4.2 后验有效性要求

候选和当前参数都必须满足：

- 回放状态为 `historical_rct_replay`；
- 后验 CAC 和人均增量订单均为有限值；
- 人均增量订单大于 0；
- 每个实际使用的推荐层具有相应 treatment 和 control 支持。

### 4.3 替换规则

候选首先要求人均增量订单不低于当前策略。如果候选 CAC 不升，则订单或 CAC 至少有一个严格改善；如果 CAC 上升，则要求订单相对涨幅不低于 CAC 相对涨幅：

```text
new_cac / old_cac <= new_pv_per_user / old_pv_per_user
```

多个候选同时通过时，依次选择：

1. 人均增量订单更高；
2. 后验 CAC 更低；
3. `C` 更小；
4. `lambda` 更小。

### 4.4 当前规则的缺口

当前代码没有强制要求“候选的后验 CAC 不超过候选 `C`”，`predicted_feasible` 也只作为诊断，没有进入最终过滤。后续建议增加：

- 后验 CAC 或其上置信界的绝对上限；
- 最低有效样本量和 propensity/support 检查；
- 动作占比上下限；
- 相对当前策略的置信区间或显著性门禁；
- 在非等概率 RCT 下使用 IPW/Hajek 或 DR，而不是简单均值差。

## 5. DFCL 应如何接入现有 EUEN

### 5.1 接在离线训练层，而不是写进线上选参任务

DFCL 要解决的是“预测损失与最终决策价值不一致”。因此主要修改点应放在现有 EUEN 训练脚本，而不是把 DFCL 做成线上实时学习任务。

当前基线训练脚本为：

- [`demo/euen_test_feature_time/euen_4t_02.py`](../../demo/euen_test_feature_time/euen_4t_02.py)

推荐先新增独立实验脚本，不覆盖基线，例如：

```text
demo/euen_test_feature_time/euen_4t_dfcl_pl_cac.py
```

保留现有 outcome/cost prediction loss，并增加 DFCL-PL-CAC：

```text
L_total = L_prediction + beta * L_decision
```

对业务 CAC 上限 `kappa`，模型预测的动作分数可写为：

```text
score_hat(i,a)
  = delta_y_hat(i,a)
    + lambda * (kappa * delta_y_hat(i,a) - delta_c_hat(i,a))
```

训练时用温度 `tau` 将硬 `argmax` 平滑为 softmax 策略，再利用 RCT 中实际 treatment 的事实 outcome/cost 和已知 propensity 构造 IPW 或 DR 决策价值损失。这样决策价值才能反向传播到 EUEN 的 uplift/cost heads。

### 5.2 在线层继续复用当前用户级规则

DFCL 模型训练完成后，在线层不需要运行反向传播，也不需要实时读取后验标签。继续执行：

```text
DFCL-EUEN 推理
  -> 读取 C、lambda
  -> 逐用户计算各动作 score
  -> argmax 选择动作
  -> 业务兜底和动作占比保护
```

现有 [`在线运筹代码.zip`](../../在线运筹代码.zip) 中的用户级拉格朗日方案可以作为在线执行层原型。DFCL 改善的是输入该执行层的 uplift/cost 预测，而不是替代整个线上参数与执行系统。

### 5.3 后验数据在 DFCL 中的三种用途

成熟、未被事后标签筛选的 RCT 数据应同时用于：

1. **离线训练**：构造 DFCL 的 factual IPW/DR decision loss；
2. **离线评估**：比较现有 EUEN 与 DFCL-EUEN 的策略价值、CAC 和动作占比；
3. **线上异步校准**：滚动选择 `C、lambda` 并监控策略漂移。

训练 decision loss 时必须使用完整 RCT 人口及真实设计概率。不能使用按“有订单/触达成功”等事后结果筛选的样本，否则会破坏因果无偏性。若预测损失确实需要重采样，可采用双数据流：重采样数据计算预测损失，完整 RCT 数据计算决策损失。

### 5.4 v5 RCT propensity 实测记录（2026-10-19）

数据窗口沿用 v5 train：`2026-05-11 ~ 2026-08-21`，排除 `2026-06-18 ~ 2026-06-22`、`2026-08-02`、`2026-08-08`、`2026-08-09`。数据源为未按 outcome 筛选的 `dm.ut_alg_flowback_msg_outcall_label_v2_di`。

当前统计先按 `pid + dt + treatment` 去掉同日同组重复，再按用户日期排序；距离上一条记录不足 7 天的同组记录视为同一次入组，间隔至少 7 天视为新的候选入组事件。窗口内共得到 `4,403,662` 次候选有效入组：

| treatment_id | treatment | 有效入组数 | propensity | 逆概率 `1/p` |
|---:|---|---:|---:|---:|
| 0 | DS空白（control） | 2,164,815 | 0.491594 | 约 2.03 |
| 1 | 留存6张3元 | 782,878 | 0.177779 | 约 5.62 |
| 2 | 8元留存5张3 | 521,821 | 0.118497 | 约 8.44 |
| 3 | 留存6张5元 | 411,671 | 0.093484 | 约 10.70 |
| 4 | 10元留存5张3 | 522,477 | 0.118646 | 约 8.43 |

结论：五组分流不均匀，但每日比例较稳定；第一版可以把上述窗口经验概率作为 v5 固定 propensity，不能假设为 `1/5`。最大基础 IPW 约为 `10.70`，暂不属于异常极端权重，但仍需在训练前检查加权样本量与 loss 尺度。

这个口径目前是“7 天去重得到的候选入组事件”，不是实验平台配置概率。业务另有“28 天后才可能重新入组”的规则，因此若后续能取得真实 assignment id、入组时间或实验配置，应优先以真实随机化事件和配置概率替换；并检查 7 天切分得到的相邻候选入组事件是否存在小于 28 天的情况。

## 6. 推荐实施顺序

### 当前最近一步：propensity 入样与 IPW 验收

在修改 EUEN loss 之前，先完成以下数据验收：

1. 在完整、未按 outcome 筛选的 v5 RCT decision-loss 样本中，根据 `fake_treatment_id` 写入上表对应的 `propensity` 和 `ipw = 1 / propensity`；
2. 保证一行对应一次有效入组事件，不能把同一次入组的多日重复记录重复送入 decision loss；
3. 按 treatment 核对样本数、propensity、IPW 加权总量和有效样本量；
4. 明确线上 3 个 treatment 到底排除 treatment 2 还是 treatment 3，并让训练 softmax mask、离线评估和线上动作集合完全一致；
5. 先用当前 EUEN 预测跑通一版 IPW/Hájek 策略价值评估，再实现 DFCL-PL-CAC，以便区分“评估链路收益”和“decision loss 收益”。

### 阶段 0：建立用户级非 DFCL 基线

```text
现有 EUEN
  -> 当前在线 C、lambda 选参
  -> 用户级 argmax
  -> RCT 后验回放
```

这一步对应 `U1`，用于确认取消分桶本身的收益和风险。

### 阶段 1：离线 DFCL-PL-CAC

- 从现有 EUEN 权重 warm start；
- 增加 DFCL-PL decision loss；
- `beta` 从 0 逐步升高，避免训练初期策略震荡；
- 先固定或从线上稳定区间采样 `C、lambda`；
- 使用完整 RCT 和真实 propensity；
- 早停指标改为验证集 DR/IPW 策略价值，而不是只看 AUUC。

### 阶段 2：影子运行

- DFCL 模型不实际下发，只产出动作；
- 与原分桶策略、用户级普通 EUEN 同期比较；
- 检查动作占比、预测成本、后验 CAC、support 和数据漂移。

### 阶段 3：小流量 RCT

建议至少比较：

| 实验组 | 模型训练 | 决策方式 | 目的 |
|---|---|---|---|
| B0 | 当前 EUEN | 分桶后验 + OR | 原线上基线 |
| U1 | 当前 EUEN | 用户级 `C、lambda` | 判断用户级决策本身的收益 |
| D1 | DFCL-PL-CAC | 用户级 `C、lambda` | 判断 decision loss 的增益 |

只有 U1 稳定且 D1 在策略价值、CAC 与置信区间上优于 U1，才建议逐步扩大 DFCL 用户级流量。

## 7. 工程注意事项

1. 明确 cost head 是总营销成本还是相对 control 的增量成本，并保证训练、打分和后验 CAC 口径一致。
2. 当前业务已确认 control cost 为 0；训练、决策和后验评估均固定使用这一口径，不增加 control cost head。
3. 线上参数任务中的 `toPandas()` 只适合有界历史数据；全量动作落表应使用 Spark SQL、DataFrame 或向量化推理。
4. 在线代码包目前主要展示参数更新和历史回放，没有完整展示全量线上动作落表/下发链路。
5. 线上 hard argmax、离线 softmax surrogate 和后验回放的动作集合必须完全一致；当前默认动作集合排除了 8 元券，需要在所有层统一。
6. 需要冻结历史用户“当时可获得”的特征和预测，禁止使用未来信息重新打分造成回放泄漏。

## 8. 最终架构

```text
完整 RCT 数据
  -> 离线 EUEN + DFCL 训练
  -> 模型发布
  -> 在线预测用户级 uplift/cost
  -> 使用已发布 C、lambda 逐用户选择动作
  -> 保留探索/control 流量
  -> 7 日后产生真实 outcome/cost
  -> IPW/DR 后验回放
  -> 更新 C、lambda；定期重训 DFCL
```

最终应采用“离线决策导向训练 + 在线轻量分配 + 后验异步闭环”，而不是在线实时训练 DFCL，也不是完全放弃历史后验。
